## 2. 設計の前提 — Mind が普通の言語と決定的に違う点

ここが本プロジェクトの技術的な核心であり、設計判断の大半がここから導かれる。

### 2.1 単語は「正規化」してから照合される

Mind のコンパイラは、ソース上の文字列をそのまま識別子として扱わない。以下の変換を行ってから
シンボルテーブルを引く。

| 規則 | 例 |
|------|-----|
| 送り仮名（漢字に続くひらがな）を削除 | `反応し` = `反応する` = `反応させる` → `反応` |
| 単語内のひらがなも削除 | `赤い色で表示する` → `赤色表示` |
| ただし先頭のひらがなは保持 | `ご案内する` → `ご案内`（≠ `案内`） |
| ひらがなのみの単語は末尾の助詞だけ削除 | `つぎに` → `つぎ` 相当の扱い |
| 中点を無視 | `トータル・カウント` = `トータルカウント` |
| 半角カナ ≡ 全角カナ（濁点は合成） | `ｶﾞ` → `ガ` |
| 半角英数記号 ≡ 全角英数記号、大文字 ≡ 小文字 | `VIDEO/8` = `video/8` = `ＶＩＤＥＯ／８` = `ｖｉｄｅｏ／８` |
| 数字に続く非数字（助数詞）は無視 | `５６０円` → `560`、`１０００円` → `1000` |
| 否定形の送り仮名はエラー | `反応させない` → コンパイルエラー |

**帰結**: ハイライトも補完も定義ジャンプも、この正規化関数 `normalize()` が正しくなければ
すべて外れる。**これを最初に作り、テストで固める。**

### 2.2 単語の区切りは「分かち書き」

区切りに使えるのは次のみ。**それ以外はすべて単語の一部**。

```
TAB / 空白（半角・全角）/ カンマ（半角 , 全角 ，）/ 読点（、）
```

したがって `赤い色で表示する` は 1 単語、`赤い色で 表示する` は 2 単語であり、
両者の間に類似性は一切ない。**改行も区切りとして働く**（ただし `または` / `かつ` は行が意味を持つ）。

### 2.3 単語は使用前に定義されていなければならない

下位の部品から順に定義する。前方参照は `仮定義` / `本定義` で明示的に行う。

```
二乗とは       仮定義。
二乗とは 本定義
	複写し、掛けること。
```

**帰結**: 単一パスのトップダウン解析でスコープが確定する。これは LSP 実装にとって非常に都合が良い。
「定義より前で参照されている」は **確実に検出できる診断**になる。

### 2.4 トップレベルの `終り。` 以降はコンパイルされない

```
終り。          ← ここでコンパイル終了
◎◎とは        ← 以降は解析対象外
```

解析器はここで打ち切り、以降の領域は「コンパイルされない領域」としてグレーアウト表示できる（付加価値）。

### 2.5 プラットフォームと文字コード（配布物を実際に開いて確認済み）

**Mind は OS ごとにバージョンが分かれている。これは検証計画に直接効く。**

| | Windows | Linux |
|---|---|---|
| 最新版 | **Version 9**（2026/08/30, 9.04） | **Version 8**（`mind-for-linux-8.0.08`, 2021/08/14） |
| 文字コード | **Shift_JIS** | **EUC-JP** |
| バイナリ | — | **x86 32bit**（ELF 32-bit LSB / Intel 80386） |
| GUI 編（`guilib`） | あり | なし |

**Mind 9 に Linux 版は存在しない。** よって手元（macOS / Apple Silicon）で動かせる実処理系は
**Mind 8 for Linux** であり、Docker の platform は `linux/amd64` ではなく **`linux/amd64`** になる。
Apple Silicon の Rosetta は 32bit x86 を扱えないため QEMU エミュレーションとなる（→ 遅い。M5 の設計に影響）。

送り仮名の削除・正規化・分かち書き・制御構文といった**言語のコアは 8 と 9 でほぼ共通**なので、
M0 の答え合わせには Mind 8 で十分。Mind 9 固有の追加単語と GUI 編だけが未検証領域として残る。

#### ファイル形式

| 項目 | 値 |
|------|-----|
| ソース拡張子 | **`.src`**（Mind WorkBench では新規作成時に強制される） |
| 実行ファイル | `.exe`（Linux は拡張子なし）+ `.mco`（M コード＝実体） |
| 辞書 | `.sym`（**バイナリ**。テキストではないので直接は読めない） |
| 履歴 | `.his`（**テキスト**。ソース名・更新日時・**リンク先ライブラリ名**・起動引数） |
| エラー出力 | `.inf`（インフォメーションファイル。**文法エラー時のみ生成**） |

VS Code の既定は UTF-8 なので対策が要る:
- ワークスペース設定テンプレート（`"[mind]": { "files.encoding": "shiftjis" }` / Linux 運用なら `eucjp`）を
  生成するコマンドを拡張に持たせる
- Language Server は VS Code から UTF-8 で受け取るので内部処理は UTF-8 のまま
- **実コンパイラ連携時のみ**、一時ファイルへ Shift_JIS/EUC-JP で書き出す。
  `.inf` に桁は入っていないので（実物で確認済み）、位置は「引用された語を行の中から探す」で決める
- 検証環境ではこの変換を `docker/bin/mindc` ラッパーが担当済み（`.mindbuild/` に EUC-JP の影ソースを作る）。
  変換は 1 行ずつの写しなので、**`.inf` の行番号はそのまま元のソースの行番号として使える**

### 2.6 コンパイル単位は「ライブラリ + ソース」

Mind のコンパイルは下位ライブラリ（`lib/file`, `lib/guilib` など）に**直列にリンク**して行われる。
どのライブラリにリンクするかで可視な標準単語が変わるため、LS も同じ情報を持つ必要がある。

- 設定 `mind.library`（既定 `file`、GUI なら `guilib`）
- **`.his` がテキストなので、既にコンパイル済みのソースはここからリンク先ライブラリを自動判定できる**
- 1 プログラムが複数ソースに分かれる（副ソースの読み出し）ケースがあるため、
  **マルチファイルのシンボル解決**を最初から設計に入れる

### 2.7 実処理系の検証環境 — **別リポジトリに分離済み** ✅

処理系の Docker 環境は [Mind-Docker](https://github.com/shin3tky/Mind-Docker) が持つ。
MindLS はそのイメージと CLI 契約だけに依存する。詳細は **`docs/COMPILER-BACKEND.md`**。

```sh
cd ../Mind-Docker && make build && make selftest   # mind-docker:8.0.08 ができる
```

UTF-8 のソース → EUC-JP → 本物の `mind` → 実行ファイル + `.mco` + `.sym` + `.his` まで、
Windows 11 + WSL2 / macOS (Apple Silicon) / x86_64 Linux で**通ることを確認済み**。

これにより次が可能になった。

| できるようになったこと | どこで使うか | Docker |
|---|---|---|
| 標準ライブラリ `.src` からの**辞書自動生成** | M4（**完了**。配布物から直接読む） | **不要** |
| 正規化規則・分かち書き・構文の**答え合わせ** | M0 の差分テスト | 必要（任意実行） |
| `.inf` の実物を得てフォーマットを確定 | M5 のパーサ実装 | 必要（オプトイン） |

**制約**: Apple Silicon ではエミュレーションになるぶん遅い。
**Language Server 本体はホスト側ネイティブの Node で動かし、コンテナは「保存時に叩くバックエンド」**
として使う。打鍵ごとの補完・ホバーは自前解析だけで完結させる。

**拡張の利用者に Docker を要求しない。** Docker から取り出したものは生成物としてコミットする。

## 3. アーキテクチャ

```
┌──────────────────────────────────────────────┐
│ vscode-mind（VS Code 拡張 / クライアント）                    │
│  ・言語登録（.src / .mnd）・TextMate 文法                     │
│  ・language-configuration.json（コメント・括弧・インデント）    │
│  ・LanguageClient 起動・設定 UI                              │
└───────────────┬──────────────────────────────┘
                │ LSP (stdio)
┌───────────────▼──────────────────────────────┐
│ mind-language-server                                          │
│  ・TextDocuments 管理 / 差分更新                              │
│  ・各 LSP ハンドラ（symbol / definition / completion / ...）   │
│  ・診断アグリゲータ（自前解析 ＋ 外部コンパイラ）               │
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│ mind-core（エディタ非依存・純 TypeScript）                     │
│                                                               │
│  normalizer.ts   文字幅/大小/中点/送り仮名の正規化             │
│  lexer.ts        分かち書き → Token[]                         │
│  parser.ts       定義・宣言・制御構文の構造化                   │
│  symbols.ts      シンボルテーブル（大域 / 局所 / 局所処理単語）  │
│  stdlib.json     標準単語辞書（名前・種別・スタック仕様・説明）  │
└──────────────────────────────────────────────┘
```

**`mind-core` をエディタから完全に切り離す**のが要点。単体テストが書きやすくなり、
将来 CLI リンタや別エディタ対応に流用できる。

### トークンの形

正規化で情報を捨ててはいけない。トークンは生テキストと正規形の両方を持つ。

```ts
interface MindToken {
  raw: string;            // "売り上げ計上とは"
  normalized: string;     // "売上計上"        ← 照合用キー
  trailingParticle?: string; // "とは"          ← 構文判定用
  kind: TokenKind;        // Word | Number | String | Char | Comment | ...
  range: Range;           // UTF-16 ベース
}
```

- **構文判定は `raw` の末尾（`とは` / `は` / `を` / `に` / `へ` / `と` / `から`）で行う**
- **シンボル照合は `normalized` で行う**

`とは`／`は` を送り仮名として消してしまうと定義が検出できなくなるため、
正規化の前に助詞を切り出して保持する。

## 4. 押さえるべき Mind の構文一覧

実装時のチェックリストとして使う。

### 4.1 定義・宣言

| 構文 | 例 |
|------|-----|
| 処理単語 | `○○とは … 。`（`とは` は `は` でも可） |
| 処理単語（属性付き） | `○○とは 処理単語 整数入力 整数入力`（改行不可） |
| 関数 | `○○とは 関数 整数入力 整数出力`（改行不可、引数 1〜3） |
| 仮定義 / 本定義 | `○○とは 仮定義。` → `○○とは 本定義 …。` |
| 整数変数 | `○○は 変数。` |
| 小数変数 | `○○は 小数変数。` |
| ワード / バイト変数 | `○○は ワード変数。` / `○○は バイト変数。` |
| 文字列情報変数 | `○○は 文字列。` |
| 文字列実体変数 | `○○は 文字列実体 長さ １００桁。` |
| 数値定数 | `○○は 定数 ２５０度。` / `○○は 定数 <Mind式>。` |
| 文字列定数 | `○○は 文字列定数 "dir /w"。` |
| 等価定義 | `○○は △△と 等価。` |
| 等価な関数 | `○○は △△と 等価な関数[2|3]。` |
| 局所変数 | 定義の冒頭に `△△は 変数`（**末尾に `。` を付けない**） |
| 局所処理単語 | 定義内にネスト。末尾 `。` なし。本体開始に `本体とは` ダミー宣言 |
| エントリポイント | `メインとは …。` |

**診断ネタ**: 局所変数に `。` を付けると処理単語の定義終了と誤認される — これは実際に起きやすいミスなので警告対象。

### 4.2 制御構文キーワード

```
もし（擬似語・無意味）  ならば  さもなければ  でなければ  つぎに
ここから  繰り返す  打ち切り  もう一度
回数指定  回数
終り  実行終り
選択する … 選択終り
事例をとる / 文字列事例をとる / 範囲事例をとる … 例外なら / 範囲外なら … 事例終り
無処理
または  かつ        ← 例外的に中置記法。影響範囲は「行」
コンパイル抑止。 … コンパイル抑止終り。
```

**対応関係の検査**（診断の主力）:
- `ならば` / `でなければ` ↔ `つぎに`
- `ここから` / `回数指定` ↔ `繰り返す`
- `選択する` ↔ `選択終り`
- `事例をとる` ↔ `事例終り`（`例外なら` は必須）
- 定義の `。` 閉じ忘れ

### 4.3 リテラル

| 種別 | 記法 |
|------|------|
| 整数 | `-123` / `－１２３`（全角可） |
| 小数 | `3.14` / `1.23E2` / `-1.23E-2`（仮数 15 桁、指数 ±308） |
| 8 進 | `8x644`（基数部は 2〜16 指定可） |
| 16 進 | `0xaf64de89` / `6800h` / `0af64de89H` |
| 文字 | `'A'` / `'漢'`（シングルクォート半角・全角可） |
| 文字列 | `「…」` / `"…"`（開閉の半/全角は統一必須、最大 158 文字） |
| 文字列の行継続 | 末尾に `続` |
| 文字列内制御コード | `＆改行＆` `＆ＣＲＬＦ＆` `＆ＴＡＢ＆` `＆ＥＳＣ＆` `＆0D0A＆` |

### 4.4 コメント

| 記法 | 注意 |
|------|------|
| `（ … ）` | **両端に空白が必要**。空白がなければ配列添字・演算優先の括弧 |
| `※` 〜 行末 | |
| `コンパイル抑止。` 〜 `コンパイル抑止終り。` | ブロックコメント相当 |

**スタック仕様コメント** `（金額 → ・）` は定義行に書かれる慣習で、
**ホバーとシグネチャヘルプの情報源として最重要**。これを構造化して取り込む。

```
売り上げ計上とは　（単価、個数　→　・）
```
→ ホバー表示: `売り上げ計上 (処理単語)  単価, 個数 → ・`

#### 実装で分かった言語の細部

実物を通したことで、マニュアルだけでは見えなかった点が 3 つ出た。

1. **キーワードは正規形で照合しなければならない。**
   `繰り返す` も `繰り返し` も正規形は `繰返`。生テキストで並べると表記ゆれで取りこぼす。
   同じ理由で `ならば` は `なら`、`ここから` は `ここ` になる（末尾の助詞が落ちる）。
2. **`ならば`（条件）と `なら`（事例のラベル）は正規形が衝突する。**
   `'e'なら　１` の `なら` も `ならば` も正規形は `なら`。
   静的解析では**生テキストの末尾が `ば` かどうか**で見分けるのが確実
   （コンパイラは文脈で判断している）。これを入れるまで標準ライブラリで 9 件の誤検出が出ていた。
3. **`仮定義` は本体を持たない宣言で、`。` が省かれることがある。**
   配布物には `○○とは　仮定義　（・ → ・）` と書かれた箇所がある。
   定義の本体開始として扱うと、以降の解析が丸ごとずれる。

#### 助数詞の扱い

`５６０円` の `円` を落とす規則は、**識別子ではなく数値リテラルの規則**だった。
`normalize()` に入れると `８ビット表示` が `8` に潰れる。
レキサ側で `{ digits, counter }` に割り、助数詞は捨てずに持っておく。
最終的な解釈は実コンパイラとの差分テストで確定させる。

#### 辞書生成ツールをパーサの上に載せ替えた

`tools/gen-stdlib-dict.ts` は独自の正規表現で定義行を拾っていたが、
パーサと突き合わせたところ **99.8% 一致**し、残る 1 件はツール側の取りこぼしだった
（`（…）` コメントを含む行で名前の先頭に `（` が入っていた）。
独自実装を捨ててパーサを使うようにしたので、解析器と辞書がずれなくなった。

### M5 — 診断 — **完了** ✅

**採用方針: 自前解析を主、実コンパイラ連携を従（オプトイン）**

#### 6.0 先に「単語の世界」を測った

未定義単語を指摘するには、**何が定義済みかを漏れなく知っている**必要がある。
そこで公式サンプル 15 本と標準ライブラリ 46 本について、単語の引用のうち
解決できないものの割合を測った。最初の辞書（`pmind/file/*.src` 由来）では

| コーパス | 未解決の引用 | 異なり語数 |
|---|---|---|
| 公式サンプル | 25.3% | 75 |
| 標準ライブラリ | 38.8% | 531 |

この数字では未定義単語の診断は出せない。内訳を潰した結果が次。

| 手当て | 効果 |
|---|---|
| カーネル組み込み単語 `pmind/kernel/c_words*.wrd` を辞書に取り込む（597 語） | サンプル 25.3% → 13.8% |
| 局所処理単語（ネストした定義）をパーサで扱う | 〃 |
| 型紙の要素、ユーザ定義型による局所宣言、日本語の属性語 | ライブラリ 38.8% → 16.1% |
| 予約語表（`入れる` `クリア` `一つ増加` …）を持つ | サンプル **5.0%** / ライブラリ **5.1%** |
| 数式表現 `［ … ］` をレキサで切る | 〃 |

残る未解決はほぼ `"x.src"を　コンパイル。` で取り込む**他ファイルの単語**。
これを追えるようにするまでは未定義単語の診断を既定で有効にできない（→ 次項の既定値）。

道すがら、実物に当てて初めて分かった取りこぼしも直した。

- 局所処理単語（`下位処理とは` … `本体とは`）を一切拾えていなかった
- `（文字列　→　変換結果、合否(1/0)）` のように括弧が入れ子のコメントを単語として読んでいた
- 同じ名前の定義が `条件コンパイル` で複数あると、後の定義が前の定義の局所シンボルを消していた

#### 6.1 自前解析による診断（常時・リアルタイム）

レキサ・パーサが出す構文レベルの診断に加えて、`packages/mind-core/src/diagnostics.ts` が
シンボルを見る診断を出す。**既定で出るものは公式コーパス 61 本に対して誤検出ゼロ**で、
これは `corpus.test.ts` が毎回確かめている。

| 検出 | 重大度 | 既定 | 設定 |
|------|--------|------|------|
| 次の定義が始まっても `。` で閉じていない | Error | 常時 | — |
| `ならば` に対応する `つぎに` がない等の構文対応ミス | Error | 常時 | — |
| `事例をとる` に `例外なら` がない | Error | 常時 | — |
| 文字列定数が 32767 文字（半角換算）超 | Warning | 常時 | — |
| 局所変数宣言に `。` を付けている | Warning | 常時 | — |
| 定義より前での参照（`仮定義` なし） | Warning | **有効** | `mind.diagnostics.forwardReferences` |
| 否定形の送り仮名（`表示しない`） | Warning | **有効** | `mind.diagnostics.negativeForms` |
| `（ ）` コメントの両端に空白がない | Warning | **有効** | `mind.diagnostics.commentParens` |
| 未定義単語の参照 | Warning | **有効**（語彙を把握しきれないときは黙る） | `mind.diagnostics.undefinedWords` |
| トップレベル `終り。` 以降のコード | Hint（グレーアウト） | 常時 | — |

当初案から変えた点。

- **重大度を Error から Warning に落とした。** 自前解析はコンパイラではない。
  確信を持って Error と言えるのは構文の対応が取れていないときだけで、
  単語の有無は辞書の完全性に依存する。Error は実コンパイラ連携（6.2）の担当にする。
- **未定義単語は一度「既定で無効」にし、取り込みを追えるようになってから反転させた**（§10・40）。
  いまは語彙を把握しきれないと分かったときだけ黙る。
- **ファイル末尾での `。` 閉じ忘れは報告しない。** 実コンパイラが通すため（§10 の実測）。
  次の定義が始まってしまう場合だけエラーにする。
- 否定形は「送り仮名が落ちるので肯定形と同じ単語になる」ことを伝える文面にした。

#### 6.2 実コンパイラ連携（オプトイン・保存時）— **完了**

設定 `mind.compiler.enabled` が `true` のときだけ有効。既定は無効。
実装は `@mindls/compiler` の `DockerCompiler`、詳しくは §10「実コンパイラ連携」。

```
保存
 └→ 常駐コンテナに docker exec（起動は 1 度きり。以降は使い回す）
      └→ ソースのあるフォルダーを丸ごと EUC-JP に変換（コンテナ内の一時領域へ）
      └→ 素の mind をそこで実行（前回の .inf は消してから）

 └→ .inf を EUC-JP から復号して解析
 └→ 行番号はそのまま使い、桁は「引用された語を行の中から探す」で決めて Diagnostic 化
 └→ 自前解析の診断に足して送る（置き換えない）
```

### M6 — 仕上げ — **完了** ✅

#### Semantic Tokens

tmLanguage は正規表現しか見ないので、`売り上げ計上し` が自分で定義した処理単語なのか
標準ライブラリの単語なのかを区別できない。Mind は送り仮名が自由に揺れるぶん、
この区別がとくに効く。シンボルテーブルを持っている側（`mind-core/src/semantic.ts`）で塗り分ける。

| 対象 | 型 | 修飾子 |
|---|---|---|
| このファイルの処理単語・関数 | `function` | 定義位置に `definition` |
| 局所処理単語 | `function` | `static`（親からしか見えない） |
| 標準ライブラリ / カーネルの単語 | `function` | `defaultLibrary` |
| 予約語（`入れる` `クリア` …） | `function` | `defaultLibrary` |
| 型名（`ファイル情報` …） | `type` | `defaultLibrary` |
| コンパイラ指示（`コンパイル` `条件コンパイル`） | `macro` | — |
| 変数・定数 | `variable` | 定数は `readonly`、宣言位置に `declaration` |
| 型紙 / その要素 | `type` / `property` | — |
| 制御構文 | `keyword` | — |
| 数式表現の括弧と演算子 | `operator` | — |

LSP の標準の型・修飾子だけを使う（独自の型は、対応していないテーマでは無色になる）。
コメント・文字列・数値は塗らない。tmLanguage で足りているうえ、複数行にまたがるトークンは
LSP の表現（1 トークン 1 行）に収まらないため。知らない語も塗らず、診断に任せる。

#### リネーム

Mind は照合の前に送り仮名を落とすので、同じ単語がソース上では
`売り上げ計上し` `売り上げ計上する` `売り上げ計上とは` と揺れて現れる。
**出現ごとの末尾の送り仮名と助詞はその場のものを残し、語幹だけ差し替える。**

```
売り上げ計上とは  →  記帳とは
１２０円を　売り上げ計上し    →  １２０円を　記帳し
２５０円を　売り上げ計上する。 →  ２５０円を　記帳する。
```

`prepareRename` で断るもの: 制御構文、予約語、このファイルに定義の無い単語（標準単語や他ファイルの単語）。
新しい名前も検査する — 区切り文字（空白・タブ・カンマ・読点）、`。`、`※`、引用符始まり、
ひらがなだけの名前は断る。既存の名前との衝突も見る。ただし `売り上げ計上` → `売上計上` のような
**表記ゆれだけを直すリネームは通す**（正規形が同じなので衝突ではない）。

#### 入力中の字下げ — フォーマッタは見送り

`language-configuration.json` の `indentationRules` / `onEnterRules` で、
定義のヘッダとブロックを開く語のあとを深く、`つぎに` `繰り返す` `事例終り` `選択終り`
`さもなければ` `例外なら` で始まる行を浅くする。正規表現だけで書く規則なので、
公式コーパスに当てて誤爆しないことをテストで確かめている。

**全文フォーマッタは作らなかった。** 理由は次の 3 つ。

- マニュアルは字下げの流儀を決めていない。実際、`ならば` を条件行と同じ深さに置く書き方と、
  ひとつ深く置く書き方が両方ある（公式サンプルは後者、マニュアルの例は前者）
- 公式ソースはタブと全角空白が混在し、行末の `※` コメントを桁で揃えている。
  行頭だけ書き換えてもこの桁が崩れる
- 整形しないことによる実害が小さい。入力中の字下げが効けば、書いている間は困らない

やるなら `ならば` の流儀を設定で選べるようにしてからにする。

#### パッケージング

npm workspaces では `@mindls/language-server` が node_modules のシンボリックリンクになっていて、
vsce はこれを .vsix に入れられない。**esbuild で拡張と Language Server をそれぞれ 1 ファイルに束ね**、
`packages/vscode-mind/dist/` に置く。辞書はバンドルに含めず `stdlib.json` として隣に置き、
`analysis.ts` がリンク → 隣のファイルの順で探す。

```sh

npm run package    # vsce package → dist/vscode-mind-<version>.vsix
```

.vsix は 12 ファイル・200 KB。`packages/vscode-mind/test/bundle.test.ts` が、
束ねた Language Server が起動して辞書も読めることを確かめる（リンクではなく隣のファイルから）。

守るのは一方向だけ。

> **実コンパイラが通すものを、我々がエラーにしてはいけない。**

逆は成り立たない（コンパイラではないので見逃しはある）。赤くしすぎないことだけを機械的に守る。

### 実コンパイラ連携（35・完了）

`@mindls/compiler` に `DockerCompiler` を入れ、Language Server の保存時に呼ぶようにした。
既定は無効（`mind.compiler.enabled: false`）。

```
保存
 └→ 常駐コンテナに docker exec
      └→ ソースのあるフォルダーを丸ごと EUC-JP に変換（コンテナ内の一時領域へ）
      └→ 素の mind をそこで実行
      └→ 終了コード・出力・.inf を目印で区切って一度に持ち帰る
 └→ .inf を復号して解析し、行と桁を付けて Diagnostic 化
 └→ 自前解析の診断に **足して** 送る（置き換えない）
```

決めたこと。

| 論点 | 決めたこと | 理由 |
|---|---|---|
| 起動コスト | **常駐コンテナ + `docker exec`** | `docker run` は毎回コンテナを作る。QEMU 経由だと特に重い |
| いつ走らせるか | **保存時だけ** | 打鍵ごとには重すぎる。自前解析が打鍵ごとを受け持つ |
| EUC-JP への変換 | **コンテナの中の `iconv`** | Node の `TextEncoder` は UTF-8 しか出せない。`iconv-lite` を足さずに済んだ |
| 何を渡すか | 中身ではなく**パス** | 保存時だけなのでディスクが最新。同じフォルダーの `コンパイル` 取り込みもそのまま解決する |
| ワークスペースの扱い | **読み取り専用でマウント** | 生成物（実行ファイル・`.mco`・`.sym`・`.his`）でユーザーのフォルダーを汚さない |
| 失敗したとき | 理由を**警告として出す** | 黙って何も起きないと、設定したのに効いていないのか分からない |
| 生成物 | コンテナ内の一時領域に置いて捨てる | `mindc` はワークスペースに `.mindbuild/` を作るので使わない |

`docker` の呼び出しは差し替え可能にしてあり（`DockerCompiler` の `run`）、
コンテナの起動・再起動・後始末・`.inf` の復号までを偽の `docker` で試せる。
実物の `.inf`（EUC-JP の原本）を流す試験も入れてある。本物のコンテナが要るのは最後の 1 手だけ。

### 取り込みの索引（40・完了）

`"x.src"を　コンパイル。` でつながるファイルを見にいくようにした。これで
**未定義単語の診断を既定で有効にできた**。

#### つながりの見かた

`WorkspaceIndex` がワークスペースの `.src` / `.mnd` / `.wrd` を走査し、取り込みの矢印を
**向きを無視して**たどる。`fhead.src` を開いているときに、それを取り込む `file.src` と、
`file.src` が取り込む他のファイルまで見えるようにするため。

取り込みの**順番は見ない**。順番まで見れば「あとで定義された単語を先に使っている」も
拾えるが、判定を外したときに正しいコードを赤くしてしまう。前方参照の検査は 1 ファイルの
中だけで行い（`forward-reference`）、ここは和集合という甘いほうに倒す。

#### 黙る条件 — ここが本題

未定義単語は、**語彙を把握しきれていないと分かった時点で黙る**。

| 黙る条件 | なぜ |
|---|---|
| 取り込み先が 1 つでも見つからない | `条件コンパイル ＤＯＳ環境` 配下の `fnamedos.src` など、Linux 版には無いファイルがある。見えていないものを未定義とは呼べない |
| `mind.library` が `file` 以外 | `guilib` の語彙は辞書を持っていない（Windows 版が要る） |
| 取り込みの関係がまったく無く、`メイン` も無い | ライブラリとして書かれた断片。どこから取り込まれるか分からない（マニュアル 02: `メイン` はプログラムの入口で、ライブラリには意図的に置かない） |

3 つめは実測で足した条件。標準ライブラリを走らせたところ、`*_source_andr.src` のような
**どこからも取り込まれていない代替実装**が 5 本残り、87 件の誤検出を出した。

#### 測った結果

| コーパス | 診断が効いたファイル | 黙ったファイル | 誤検出 |
|---|---|---|---|
| 公式サンプル（15 本 + 取り込み先 1 本） | 13 | 3 | **0** |
| 標準ライブラリ（46 本） | 0 | 46 | **0** |

標準ライブラリが全部黙るのは正しい。あれは単体で完結したプログラムではなく、
`file.src` から順に取り込まれる断片の集まりで、しかも Linux 版には無いファイルを
条件付きで取り込んでいる。
